# Безопасность сейвов и экономики

Документ описывает модель доверия в облачных сохранениях, векторы мошенничества,
что уже закрыто и что осталось. Обновлять при изменении схемы сейва.

## 1. Модель доверия

| Где | Что хранится | Кому доверяем |
|---|---|---|
| Клиент (браузер/Telegram WebView) | весь прогресс, `localStorage`, `S` | **никому** — это чужая машина, код можно подменить |
| Сервер + Redis | `cloudsave:{user_id}`: `{data, saved_at, user_id, version}` | источник правды по версии и времени |
| Telegram | подпись `initData` (HMAC с токеном бота) | только после проверки подписи и `auth_date` |

Главное правило: **сейв с клиента — это недоверенный ввод**, а не состояние игры.
Сервер обязан проверять форму, но он не может проверить «честность» чисел, пока
правила экономики живут на клиенте (см. §5).

## 2. Векторы мошенничества через механику сейвов

| # | Вектор | Как эксплуатируется | Статус |
|---|---|---|---|
| 1 | «Отмывание» подменённого прогресса | правим `localStorage`, сохраняемся — сервер запоминает и раздаёт это на все устройства | **частично закрыто**: кошелёк ограничивает баланс, отчёты — доход, проверка возможностей — прирост планет/систем (флаг/`CAPABILITY_ENFORCE`) |
| 2 | Строка/`null` вместо числа | `dust: "1e999"` → `NaN` в экономике; `NaN < цена` = `false` → бесповарная покупка | **закрыто** (типы полей) |
| 3 | Отравление прототипа | `{"__proto__":{"...":...}}` → `Object.assign(S, save)` загрязняет прототип | **закрыто** (сервер + клиент) |
| 4 | Гигантские/битые сейвы | 800 КБ мусора каждые 5 с → расход Redis и парсинг в админке | **закрыто** (лимиты глубины/узлов/строк, квота 300 сохранений/час) |
| 5 | Подделка `initData` | свой аккаунт вместо чужого | **закрыто** (HMAC + сравнение постоянным временем + числовой `user.id`) |
| 6 | Replay `initData` | перехваченный `initData` живёт 24 ч: чтение и перезапись чужого сейва, создание инвойсов | **частично** (24 ч окно, лимиты запросов; нужен короткий TTL) |
| 7 | Перебор/долбёжка API | нагрузка на сервер и Upstash | **закрыто** (лимиты `/api/load` 120/мин, `/api/save` 5 с + 300/час) |
| 8 | Гонка версий | старый клиент затирает чужой прогресс | **закрыто** (оптимистическая блокировка `baseVersion`, 409) |
| 9 | «Слепая» запись без версии | запрос без `baseVersion` проходил всегда | **закрыто** (требуется актуальная версия) |
| 10 | Админ-выдача теряется | `/admin/api/.../give` менял `saved_at`, но не `version` → клиент затирал выдачу | **закрыто** (инкремент версии) |
| 11 | Скачок ресурсов за секунды | «наиграл» 1e12 пыли за 20 секунд | **логируется** (`save_flag:{id}`), без автобана |
| 12 | Фарм офлайн-прогресса через `lastTick` | откат метки времени → до 8 ч дохода за каждую правку | **закрыто** (офлайн считает сервер по `saved_at`; клиентский `lastTick` больше не решает) |
| 13 | Бесплатный премиум | `shieldUntil`/`boosters` правятся в сейве, награда выдаётся клиентом | **частично**: щит — серверное право в Redis; лут сундука выбирает сервер (`lib/chest.js`); `shieldUntil` на 30 дней — флаг `shield_forged`; остался бустер за металлы |
| 14 | Восстановление покупки | переустановка = потеря щита/сундука | **закрыто для щита** (`entitlement:shield:{id}` при `load`); сундук выдаётся один раз по записи `purchase` (`granted`), но без серверного инвентаря |

## 3. Что реализовано

- `lib/economy-actions.js`: серверное право на премиум-щит (`nextShieldEntitlement`,
  `overlayShieldEntitlement`, `isShieldSuspicious`). Право живёт в Redis
  (`entitlement:shield:{id}`), в сейв попадает только «на большее».
- `/api/claim`: выдаёт право на щит после оплаты и возвращает его клиенту;
  проверяет, что продукт существует.
- `/api/load`: накладывает право на сейв — покупка восстанавливается на любом
  устройстве и после переустановки.
- `lib/chest.js`: награду платного сундука выбирает сервер по весам из `CHEST_CFG`,
  ключ сохраняется в записи `purchase` и возвращается клиенту; рулетка только
  доигрывает результат (локальный RNG — fallback без сети).
- `lib/save-validation.js`:
  - `validateSaveData()` — форма, типы, лимиты, `stage` из `STAGES`, зажим `lastTick`.
  - `detectSaveAnomalies()` — скачок ресурсов, откат `lastTick` (флаги, не блок).
  - `validateInitData()` — HMAC, `timingSafeEqual`, свежесть, проверка `user.id`.
- `server.js`:
  - `/api/save`: валидация → размер → квота → rate limit → версия → аномалии → запись.
  - `/api/load`: лимит запросов на пользователя.
  - CORS: при заданном `ALLOWED_ORIGIN` чужие сайты не получают заголовки.
  - админ-правки поднимают версию.
- `js/cloudsave.js`: `sanitizeCloudSave()` перед применением облака — опасные ключи,
  глубина, нечисловые значения.
- `lib/game-core.js`: те же `js/*.js` (config, physics, state, economy, invasions)
  загружаются в vm-контекст без DOM. Сервер вызывает настоящие `dustPerSec()`,
  `energyPerSec()`, `civPerSec()`, `getResourceCap()` — без копипасты формул.
- `/api/load`: офлайн-доход считает **сервер** по серверному `saved_at`
  (эффективность и часы накопления — из `CFG`/`STORAGE_CFG`), ответ содержит
  `offline`; клиент применяет его и фиксирует ближайшим сохранением.
- `js/cloudsave.js`: при равной версии, но с серверным `offline`, клиент
  принимает данные сервера (локальные часы больше не решают).
- Тесты: `tests/save-validation-test.js`, `tests/game-core-test.js` (паритет
  серверных и клиентских формул), `tests/cloud-sync-test.js`,
  `tests/economy-actions-test.js`, `tests/wallet-test.js`.
- `lib/wallet.js` + `/api/action` (**вариант C, этап 1**, флаг `SERVER_AUTHORITATIVE=1`):
  сервер хранит баланс пыли/энергии/цив (`wallet:{id}`), сам начисляет пассивный
  доход и доход за клики (батчи раз в 3 с). На сохранении траты принимаются
  всегда, а прирост — только до серверного баланса + допуск на награды.
  При обрезке в ответе приходят `clamped` и `data`, клиент сразу берёт серверный
  баланс (тост «Баланс сверен»).
- `lib/reward.js` + `/api/reward` (**этап 1б**): клиент периодически присылает
  «сколько заработал сверх пассивки» (миссии, кометы, частицы, ежедневные),
  сервер разрешает не больше `rate * seconds * REWARD_EXTRA_SHARE` и зачисляет
  в кошелёк. Интервал берётся по серверным часам; при равной версии клиент
  не затирается — чтобы не потерять офлайн-награды.
- `lib/capability.js` + проверка в `/api/save` (**этап 1в**): прирост стоимости
  планет и систем (по `planetCost`/`systemCost` из `game-core`) должен быть
  покрыт тем, что игрок реально потратил (разница между серверным балансом и
  присланным) плюс бюджет на платные сундуки. По умолчанию — флаг
  `phantom_capability`; при `CAPABILITY_ENFORCE=1` сейв отклоняется.

## 4. Что осталось (и почему это не «две строки»)

1. **Онлайн-прогресс частично серверный.** За флагом `SERVER_AUTHORITATIVE=1`
   сервер владеет балансом ресурсов и сам начисляет пассив/клики (см. §3). Пока
   ежедневных — отчётом `/api/reward`, поэтому допуск можно снижать
   (`WALLET_ALLOWANCE_SHARE=0` после проверки логов). Оффлайн-миссии и кометы
   при включённом кошельке тоже идут через отчёт; в редких случаях они могут
   обрезаться по `REWARD_EXTRA_SHARE` — смотреть флаги `wallet_clamp:*`.
2. **Премиум-сундук и бустер пока клиентские.** Щит за Stars уже живёт в Redis
   (`entitlement:shield`), но награда сундука (случайный Прайм-объект) и бустер
   за металлы выдаются на клиенте — для них нужен серверный RNG/инвентарь.
3. **Нет автобана.** Флаги пишутся в `save_flag:{id}`, решение за человеком.
4. **24-часовое окно `initData`.** Риск только при утечке `initData` (например,
   через сторонний код на странице игры).

## 5. Альтернативные архитектуры сейвов

### A. Текущая (snapshot + версия) — сделано
Клиент присылает весь сейв. Плюсы: просто, поддерживает офлайн, дешево.
Минусы: сервер хранит, но не понимает данные → читерство «правдоподобными» числами.

### B. Server-validated snapshot (гибрид) — сделано в этой итерации
То же, что A + проверка формы, лимиты, флаги аномалий. Закрывает структурные и
API-атаки, не закрывает подмену значений.

### C. Server-authoritative state (правила на сервере) — начато
Сервер хранит ресурсы и **сам считает** доход от времени: при `/api/load` отдаёт
состояние на момент запроса, клиент только рисует. Покупки/апгрейды — отдельные
эндпоинты с проверкой цены на сервере.
Плюсы: закрывает 90% читерства (нельзя «прислать» 1e12 пыли — её некому прислать).
Минусы: перенос формул из `economy.js`/`config.js` на сервер, офлайн-доход считает
сервер, сейв становится «состояние + last_server_time». **Сделано в этой итерации:**
формулы уже крутятся на сервере (`lib/game-core.js`) и офлайн-доход считается им;
осталось сделать серверным онлайн-прогресс и покупки.

### D. Event-sourced / дельты действий
Клиент шлёт не состояние, а действия (`click`, `buy`), сервер применяет валидацию
и хранит журнал + периодический снапшот.
Плюсы: максимальная защита, аудит, откат.
Минусы: нужен антифрод по частоте действий (rate/pattern), объём журнала,
сложное восстановление, задержки при плохой сети.

### E. Web3 / on-chain (как в играх с токенами)
Игровые ассеты (NFT/токены) — в блокчейне, остальное — off-chain.
Плюсы: торгуемость, публичный аудит владения.
Минусы: комиссии, задержки, кошелёк в UX; **не решает** проблему клиентского
читерства в самой игре — прогресс всё равно считает сервер.

### Про Tiny Verse
Публичной технической документации по их модели сохранений найти не удалось:
доступные источники описывают игру (Telegram-кликер/стратегия про развитие
галактики), а не архитектуру хранения. Утверждать, что у них конкретно
«event-sourced» или «on-chain», было бы догадкой. Если нужна именно их схема —
надо смотреть их клиент/API (вскрытый webview bundle), а не статью-обзор.

## 6. План миграции к C (без «переписать всё»)

1. ✅ Готово: общий модуль `lib/game-core.js` — сервер запускает те же `js/*.js`
   в vm и считает доход/лимиты настоящими функциями (есть тест на паритет).
2. ✅ Готово (за флагом): `lib/wallet.js` + `/api/action` — сервер хранит баланс,
   начисляет пассив и клики, сверяет сейв (траты — да, прирост — в пределах).
3. Клиент: получать состояние с сервера, действия (покупки) отправлять на сервер,
   локальный сейв — только кэш для офлайна.
4. Премиум: серверный инвентарь (`shield_until`, `chests`) по записям покупок,
   клиент только отображает.
5. Античит-флаги из §2.11 — в админку, с ручной модерацией.

## 7. Как включить серверный кошелёк

1. Залить `lib/wallet.js` и новый `server.js`.
2. В env Render добавить `SERVER_AUTHORITATIVE=1` (без неё всё работает по-старому).
3. По желанию: `WALLET_ALLOWANCE_SHARE` (допуск на награды, по умолчанию 0.05;
   после проверки логов можно ставить 0), `MAX_CLICKS_PER_SEC` (30)
   `REWARD_EXTRA_SHARE` (во сколько раз «прочий» доход может превышать
   пассивный, по умолчанию 2.0).
4. Для проверки возможностей: по умолчанию только флаг `phantom_capability`.
   Включить блокировку — `CAPABILITY_ENFORCE=1` (после недели чистых логов).
   Пересчёт энергии/цив в пыль — `ENERGY_TO_DUST` (1e6) и `CIV_TO_DUST` (1e9).

⚠️ Порядок выката: сначала новый клиент (`js/cloudsave.js`, `js/economy.js`
с отчётами о кликах), и только потом флаг. Старый клиент не знает про кошелёк
и его сохранения будут обрезаться по допуску.
4. После включения смотреть логи: `[save] user=… обрезаны ресурсы: …` и
   `save_flag:{id}` — это либо подмена, либо слишком узкий допуск.

Откат: убрать `SERVER_AUTHORITATIVE` и передеплоить; сейвы не меняются,
кошелёк просто перестаёт использоваться (данные в `wallet:{id}` остаются).
