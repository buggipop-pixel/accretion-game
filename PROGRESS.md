## Сессия: починка звука — фон не возвращался после «Выкл → Вкл»

**Проблема:** если выключить звук и включить обратно, фоновый эмбиент мог больше не запуститься (замечалось на фоновой музыке); также звук «умирал» после того, как браузер усыплял AudioContext.

**Причины:**
- `unlockAudio()` выходил по раннему `if (isAudioUnlocked) return;` — повторного `audioCtx.resume()` не было, поэтому уснувший контекст больше не будился.
- `toggleSound()` при включении вызывал только `unlockAudio()`, который сразу возвращался — `startAmbient()` не вызывался вообще, и музыка не возвращалась.
- `startAmbient()` ставил `ambientSource` до результата `play()`; если play() отклонялся автоплей-политикой, флаг «уже играет» оставался навсегда и фон было невозможно запустить.
- Каждое включение создавало новый `<audio>`-элемент, старые не освобождались.

**Что сделано:**
- `js/audio.js` — `unlockAudio()` больше не выходит по флагу: всегда делает `resume()` для не-running контекста и вызывает `startAmbient()` (он сам проверяет, играет ли фон).
- `startAmbient()` — один переиспользуемый `ambientAudio`, guard по `paused`, сброс `ambientSource` при отклонённом `play()`, проверка `S.settings.sound`.
- `stopAmbient()` — ставит на паузу и сбрасывает `currentTime` в try/catch, не создаёт рекурсию через `ambientSource.stop`.
- `toggleSound()` — явно делает `resume()` + `startAmbient()` при включении и `stopAmbient()` при выключении.
- `visibilitychange` — при возврате на вкладку будит контекст и возобновляет фон без клика.
- `tests/audio-test.js` — 24 регрессионных теста (моки AudioContext/`<audio>`): «Выкл → Вкл» возвращает музыку, отклонённый play не «залипает», уснувший контекст просыпается, звук не плодит элементы, «выкл» не запускает фон.

**Проверка:** `node tests/audio-test.js` — 24/24; полный набор (`npm run test:all`) — без провалов, добавлен скрипт `npm run test:audio`.

## Сессия: защита Прайм-систем (вспышка + вторжения)

**Проблема:** при тесте вспышки сверхновой из двух Прайм-объектов (кротовая нора 3 ур. + чёрная дыра) выживала только чёрная дыра. Плюс Прайм-системы могли быть целью вторжения и получать урон, как обычные.

**Причина:**
1. `performSupernova()` сохраняла только записи из `S.otherSystems` с флагом `isPrime`. Прайм на активной (в т.ч. родной) системе жил в `S.primeSystem` и в сейв не попадал — после вспышки терялся.
2. Старые сейвы могли хранить `primeData` без флага `isPrime` — система считалась обычной и вылетала по лимиту.
3. `spawnInvasion()` включал Прайм-системы в список целей; `applyInvasionAftermath()`, `applyInvasionHit()` и `applySystemLosses()` могли повреждать планеты Прайма.

**Что сделано:**
- `js/state.js` — единые хелперы `isPrimeSystemData()`, `primeDataOfSystem()`, `isPrimeSystemAt()`, `bestPrimeWormholePct()`, `markPrimeSystem()`; миграция сейвов нормализует `primeData` ↔ `isPrime` (в т.ч. для родной системы).
- `js/prestige.js` — при вспышке сохраняются ВСЕ Прайм-системы: активная/родная (`S.primeSystem`), записи из `otherSystems[0..]`, в т.ч. без флага `isPrime`. Бонус кротовой норы берётся от лучшей норы среди всех Праймов. Праймы не входят в лимит обычных систем.
- `js/invasions.js` — вторжения больше не выбирают Прайм-системы целью; старые атаки на Прайм снимаются без урона; урон планет применяется к атакованной системе, а не всегда к активной.
- `js/economy.js` — офлайн-урон и «потери систем» не трогают Прайм.
- `js/ui.js`, `js/main.js` — Прайм в списке систем и на карте определяется и по `primeData`, а не только по `isPrime`.
- `tests/prime-protection-test.js` — регрессионные тесты (вспышка с активным/родным Праймом, сейв без `isPrime`, вторжения). Добавлен в `npm run test:all` и `npm run test:prime`.

**Проверка:** `node tests/prime-protection-test.js` — 15/15; полный набор тестов — без провалов.

## Сессия: полноэкранный режим в Telegram на телефоне

**Проблема:** на телефоне кнопка ⛶ показывала «Полный экран недоступен». Причина — сломанный путь к SDK: `@twa-dev/sdk@7.0.0/dist/telegram-web-app.js` отдаёт 404 (файл называется `telegram-web-apps.js`, с «s»), поэтому `window.Telegram.WebApp.requestFullscreen` либо отсутствовал, либо был из старой версии 7.0 без fullscreen. Плюс проверка требовала `isVersionAtLeast('8.0')` ещё до попытки вызова.

**Что сделано:**
- `index.html` — SDK 8.0.2 по верному пути `dist/telegram-web-apps.js` (jsDelivr + unpkg-фолбэк).
- `js/main.js` — `_tgFullscreenAvailable()` ориентируется на наличие `requestFullscreen`, а не на строку версии; на iOS нативный API не вызывается (его там нет); добавлен обработчик `fullscreenFailed` с точной причиной; автозапрос при старте убран.
- `tests/smoke-test.js` — проверка, что SDK грузится по верному пути.

**Проверка:** `node tests/smoke-test.js` — 19/19; `node tests/prime-protection-test.js` — 23/23.

**Важно:** Telegram WebView кэширует JS — после деплоя нужно закрыть и заново открыть мини-приложение (или очистить кэш Telegram).
